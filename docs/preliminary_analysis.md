## 2. ОСТАВШИЕСЯ УЯЗВИМОСТИ И ОШИБКИ

### 🔴 Критичные

**У1. Подпись пакетов необязательна.**
apply.ts:26 проверяет подпись только `if (p.sig)` — пакет БЕЗ подписи принимается как ни в чём не бывало. Значит любой, кто знает формат `LIP:`, может подменить задания/пользователей/журналы. Нужен режим «только подписанные пакеты» после ввода ключа цеха.

**У2. Дефолтный HMAC-ключ `LIP-default-dev-key`.**
security.ts:24: пока начальник не ввёл ключ цеха, все устройства подписывают одинаковым открытым ключом из исходников. Формально защита «включена», фактически — нет. Плюс ключ лежит в localStorage без всякой защиты.

**У3. Демо-пользователи с паролями в открытом тексте.**
db/index.ts:175–180 (`admin123`, `master123`...). Хеширование применяется только при миграции/смене пароля. В демо-режиме пароли известны из README и утекают в пакетах `user`. Для боевого запуска это точка входа.

**У4. Нет тестов вообще.**
Ни одного `.test.` файла, npm-скрипта `test` нет. Критичные функции encode/decode/apply/signature не защищены регрессией — любая правка может молча сломать цепочку данных (как уже случалось с BLE).

### 🟠 Значимые

**У5. Mesh-ретрансляция только у чата.**
README/DATA_FLOW обещают mesh для всех данных; фактически TTL+ретрансляция реализованы лишь в ChatModule. Журналы/задания ходят точка-точка.

**У6. Конфликты решаются по часам устройств.**
`updatedAt` сравнивается напрямую; рассинхрон часов на телефоне цеха = потерянные обновления. Нужны логические часы (lamport) или привязка к мастер-узлу.

**У7. Контрольная сумма 8-бит + дедупликация по `len:crc`.**
Коллизии вероятны при большом потоке пакетов (mesh). CRC32 или включение from+ts в ключ дедупликации решают вопрос.

**У8. Заглушки комнат.**
Склад — `StorageModule.tsx` (7 строк). Старые `*Module.tsx` (slurry, coating, calendaring, assembly) лежат рядом с реальными Room-комнатами — мусор, путает навигацию и анализ.

**У9. Раздувшиеся файлы.**
SortingRoom.tsx — 790 строк, CoatingRoom — 540, CalendaringRoom — 528. Принцип «одна комната = переписываемый блок» нарушается: правка одной функции требует чтения всего файла. Нужен вынос вкладок в подсекции (по образцу AssemblyRoom).

**У10. CI: подпись APK временным ключом.**
Без секретов KEYSTORE_* собирается ключ с паролем `changeit`, который пересоздаётся — обновления «поверх» не встают. Инструкция в ANDROID_BUILD.md есть, но секреты не заведены.

**У11. allowBackup=false, но экспорта базы нет.**
При переносе на новый телефон журнал замесов/намазки/каландра не перенести. Нужен экспорт/импорт IndexedDB в файл (он же пригодится для резервных копий цеха).

### 🟡 Малые

- **О1.** Синхронизация версий: Dexie v13, но порядок объявлений версий местами не соответствует нумерации шагов — риск при откате ветки.
- **О2.** Тип `forced-push` определяется по набору полей (хрупко); нужен явный discriminator.
- **О3.** `SyncModule` — демо с фиктивными устройствами (может ввести пользователя в заблуждение).
- **О4.** Предупреждения vite о размере бандла (>500 КБ) — не критично для локального PWA, но замедляет первую загрузку на слабых телефонах.
- **О5.** README местами расходится с фактическим состоянием (упоминает старение, которого больше нет).

## 3. План доработок (по приоритетам)

### Этап А — Безопасность контура (делать первым)
- **А1.** Обязательная проверка подписи: если в устройстве задан ключ цеха — принимать ТОЛЬКО пакеты с валидной подписью; без ключа — честно показывать предупреждение «сеть не защищена». *(закрывает У1)*
- **А2.** Убрать dev-fallback ключа: первый запуск = обязательный экран «Задайте ключ цеха» для начальника. Хранение ключа — через Keystore Capacitor на Android. *(У2)*
- **А3.** Демо-пользователей: пароли сразу в PBKDF2-хешах; в README убрать реальные пароли, заменить на «спросите у мастера». *(У3)*
- **А4.** Поле `sig` добавить в canonical-строку дедупликации BLE. *(частично У7)*

### Этап Б — Надёжность данных
- **Б1.** Тесты (vitest): encode↔decode, sign↔verify, apply-конфликты, миграции Dexie. Минимум 15 кейсов на ядро. *(У4)*
- **Б2.** Lamport-часы поверх updatedAt (счётчик + узел) — конфликт разрешает не «кто громче», а причинный порядок. *(У6)*
- **Б3.** Дедупликация mesh: ключ = sha256(payload)+from+ts вместо len:crc8. *(У7)*
- **Б4.** Mesh-ретрансляция для ВСЕХ типов пакетов (перенести логику чата в общий слой transfer). *(У5)*

### Этап В — Структура кода
- **В1.** Удалить все старые `*Module.tsx`-заглушки; комната Склада — либо минимальная рабочая (учёт рулонов на входе), либо этап исключается из цепочки. *(У8)*
- **В2.** Декомпозиция гигантов: SortingRoom/CoatingRoom/CalendaringRoom разбить на вкладки-файлы (шаблон: AssemblyRoom + станции). *(У9)*
- **В3.** SyncModule: либо сделать реальным (статус BLE-очередей), либо удалить. *(О3)*

### Этап Г — Эксплуатация
- **Г1.** Секреты keystore в GitHub Settings → Secrets (инструкция в ANDROID_BUILD.md) — стабильная подпись, обновления поверх. *(У10)*
- **Г2.** Экспорт/импорт всей базы в JSON-файл (резервные копии, перенос между телефонами). *(У11)*
- **Г3.** Обновить README/DATA_FLOW в соответствии с фактом (без «старения», с формировкой и вальцовкой). *(О5)*
- **Г4.** Лень-загрузка комнат (React.lazy) — уменьшить стартовый бандл. *(О4)*

### Этап Д — Отложено до релиза
- **Д1.** Тест BLE на двух живых телефонах (решение пользователя).
- **Д2.** Геймификация (по первоначальному плану — на поздних этапах).

## 4. Рекомендуемый порядок

```
А1 → А2 → А3 → Б1 → Г1 → Б4 → В1 → В2 → Б2 → Б3 → Г2 → В3 → Г3 → Г4 → А4 → Д1 → Д2
```

Логика: сначала закрыть дыру «пакет без подписи проходит» (А1–А3), затем сетку тестов (Б1), чтобы последующие правки не ломали цепочку незаметно; структурные чистки (В) — после того как поведение зафиксировано тестами.
