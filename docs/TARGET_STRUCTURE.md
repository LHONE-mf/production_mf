# ЦЕЛЕВАЯ СТРУКТУРА ПРОЕКТА (target architecture)

> **Важно:** это целевая организация кода, а НЕ список файлов, которые нужно создать одновременно.
> Реальное состояние проекта всегда сверяется с `docs/PROGRESS.md` и репозиторием.
> Двигаться к этой структуре будем поэтапно (по одному модулю за шаг), без «больших взрывов».

## Принципы переходов к цели

1. **Постепенность.** Один шаг = один переезд (файл/папка) + обновление импортов + сборка + коммит + проверка на GitHub. Никаких «переезжаем всё сразу».
2. **Совместимость.** При переносе оставляем тонкие реэкспорты по старым путям, чтобы ничего не сломать; удаляем их отдельным чистым коммитом после проверки.
3. **Сервисный слой отдельно от UI.** Логика расчётов/валидаций уезжает из компонентов комнат в `production/*`; компоненты становятся тонкими (только рендер + вызов сервиса). Это продолжение начатой декомпозиции крупных файлов.
4. **transfer — единственный канал данных.** Любой обмен идёт через packet→validation→apply; outbox/inbox добавляют очереди для надёжной BLE-раздачи.
5. **stages/* неприкосновенны по содержанию.** Переезд меняет пути файлов, но не поведение комнат (проверяем цепочку DATA_FLOW.md).

## Порядок работ (предлагаемый, подтверждается пользователем)

| Этап | Что делаем | Почему именно так |
|------|-----------|-------------------|
| T1 | `core/db/migrations.ts` — вынести версии Dexie из index.ts | самый маленький безопасный переезд, разгружает index.ts |
| T2 | `core/store/` — переезд authStore/taskStore в core | готовит базу для permissions.ts |
| T3 | `core/permissions.ts` — матрица прав ролей (сейчас проверки разбросаны по UI) | закрывает уязвимость из preliminary_analysis (B-блок) |
| T4 | `transfer/validation.ts`, `conflictResolver.ts` — вынести из apply.ts | apply.ts растёт, ему нужна граница ответственности |
| T5 | `transfer/outbox.ts` + `inbox.ts` — очереди для BLE/QR | фундамент mesh-ретрансляции для всех пакетов |
| T6 | `production/batches` + `operations` — вынести логику из SlurryRoom/журналов | продолжает декомпозицию крупных компонентов |
| T7 | `production/traceability` — номер АК как единый сервис | фиксирует то, что сейчас «зашито» в 3 комнатах |
| T8 | `modules/reports` — переезд KpiDashboard | UI-слои приводим к modules/stages |
| T9 | `stages/storage` + `production/inventory` — полноценная комната Склад | единственная оставшаяся заглушка этапов |
| T10 | `modules/sync` — замена мока SyncModule на syncService.ts | убираем фиктивные устройства |

Каждый этап завершается по протоколу: tsc+vite build → commit → push → ls-remote + свежий клон → обновление PROGRESS.md (правило 9).
