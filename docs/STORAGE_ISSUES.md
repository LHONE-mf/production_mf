# Controlled production material handoffs (S4 / D2)

Storage provides a separate **Запросы и выдача в производство** section. It is accessible to a proved production user without assigning warehouse access. The server discovers the batch's actual approved route step and workshop; requester and assigned recipient scope is never inferred from client-provided workshop names. Material names/codes, batch codes and recipient names accompany stable identities. Every write has a reason and evidence reference.

| State / action | Current authority | Stock effect |
| --- | --- | --- |
| Request | Warehouse operator/Manager/Chief, or current member of the selected batch-step workshop | None; material/quantity/batch/step/recipient intent only |
| Reserve | Chief or explicit Warehouse Manager | Reserve exact requested quantity from one released, unexpired container; never another handoff's reservation |
| Approve / explicitly reapprove | Chief or explicit Warehouse Manager | None; binds immutable approval to the exact source stock revision |
| Dispatch | Chief or explicit Warehouse Manager, with matching current approval | Deduct on-hand and the exact owned reservation once; preserve source material/lot/location/expiry/batch/recipient provenance |
| Receive | Exact assigned recipient with current membership and device proof | None; acknowledges actual physical delivery, including if a batch is subsequently held |
| Cancel before dispatch | Manager/Chief; original requester may cancel an unreserved request | Release only the owned reservation; retain all request and approval evidence |

The ordinary production Master role has no Manager authority. This version deliberately requires Chief/Manager to confirm final physical dispatch as well as approval; it does not delegate debit to an operator. The original approver must remain active with Chief/explicit Manager authority and a nonrevoked device. Source changes require explicit reapproval. QA hold/block/rejection, expiry, missing reservation, inactive production batch/order, changed recipient membership and stale revisions prevent new dispatch. A reservation, approval, dispatch and recipient receipt are separate events; **none records actual production consumption**. Partial issue refers to an exact quantity from the source container; it does not create multiple tracked warehouse packages or substitute for S6 splitting.

## Authenticated contract

All routes require a current bearer session and session-bound `x-device-proof`. Writes additionally require the original `x-inventory-epoch`. Authorization is checked again after waiting for the same organization inventory/restore lock used by stock and QA writers. Production-only reads reveal own requested/assigned handoffs within current workshop membership, without warehouse stock balances or unrestricted stock/catalogue access.

- `GET /inventory/issues/context?deviceId=...`: exact organization/actor/device, warehouse level or null, epoch and posting state. It does not grant warehouse access or rebind the stock stream cache.
- `GET /inventory/issue-batches`: accessible active batch/route-step choices, UUID/step cursor (`after`, `afterStep`); `GET /inventory/issue-options?productionBatchId=...&stepNumber=...&resource=materials|recipients`: scoped active material names/base units or actual active workshop recipients.
- `GET /inventory/issues`: warehouse-wide or production-own handoffs, UUID cursor and separately validated display labels. `GET /inventory/issue-sources?issueId=...`: Chief/Manager-only compatible source containers and exact balances. `GET /inventory/issues/:issueId/history`: immutable scoped sequence history. List limits are 1–100; the UI loads 50 with explicit continuation.
- `POST /inventory/issues`: `{operationId,issueId,deviceId,materialId,productionBatchId,stepNumber,recipientId,quantity,reason,evidence}`. Quantity is a positive safe integer in the material's immutable base unit.
- `POST /inventory/issues/:issueId/operations`: `{operationId,deviceId,kind,expectedIssueRevision,reason,evidence,...}`. `reserve` adds `stockId,expectedStockRevision`; `approve`/`dispatch` add `expectedStockRevision`; `cancel` requires `expectedStockRevision` when releasing stock; `receive` has no stock fields. Unexpected fields are rejected.

New acceptance returns 201 `{status:'confirmed',operationId,issue,stock?}`. Exact same actor/device/body/ID retry returns the original acceptance with status `duplicate` and HTTP 200, even after later workflow steps; the current state is read separately. Changed ID reuse returns 409, including reuse between handoff and existing stock endpoints. Cross-scope targets fail closed (403/404); revision/state/eligibility conflicts return 409; missing history returns 428. Unknown transport/server outcomes preserve the original ID for explicit retry.

Migration **026** adds issue projections, immutable workflow events, nullable ownership on existing reservations, tenant-bound references, global cross-ledger intent collision guards and deferred physical-debit/approval pairing. Existing stock balances remain exclusively in `inventory_stocks` and `inventory_operations`; there is no second stock ledger. Stock-affecting handoff events pair with existing `reserve`, `issue`, or `release_reservation` ledger events in one transaction. DB guards independently deny operator approval and unpaired issue debit. Existing reservations, receipts, QA evidence and catalogue versions survive the populated upgrade.

## Durable intent and recovery

No Dexie reset or table version change: the existing v7 draft table holds a separate original server/org/actor/device/local-profile `issue` namespace. Requests and assigned-recipient proposals may be frozen offline from a previously explicitly loaded scope/route selection. Privileged preparation checks current online authority, original screen epoch and stock history. Every send is deliberate, rechecks live authority/history, and sends the original frozen body. Reconnect never posts automatically.

An accepted response is validated against the frozen issue and exact stock transition. Stock cache, retained stock ACK and accepted draft response commit atomically; a conflicting retained ACK rolls back local acceptance. Request/approval/recipient ACKs remain in the durable original proposal. Lost responses retain pending intent; stale/rejected responses retain original revisions, reason and evidence. Logout/account switching hides the prior scope and does not erase evidence.

Old-epoch proposals are held and never rebound automatically, including after stock-cache recovery. The ordinary Chief recovery evidence includes this namespace and retained stock ACKs. A production recipient is not assigned a warehouse grant to use recovery: retain the original operation/issue/epoch and compare the scoped handoff history and Chief's restored ledger before explicitly making any replacement intent. No automatic repost or claim of delivery is made when the original outcome is unknown. Full cross-feature restore/recovery and practical conflict handling remain part of S10.

Client tests cover offline frozen/reopened intent, malformed reads/ACKs, changed epochs and screen history, exact stock balances, conflicting retained evidence and lost ACK after original expiry.

The actual Chromium smoke uses Chief and operator profiles plus a production-only recipient, freezes an offline request across cold reload, drives every screen, loses the committed dispatch response, retries once, and checks the independent PostgreSQL ledger. The dump/restore drill restores both stock and handoff audit, retries the original dispatch unchanged, and repairs only deliberately damaged disposable projections while posting is stopped. Route A's native harness also freezes the issue request across actual force-stop/relaunch, drives Chief approval/dispatch with lost ACK, assigned receipt and independent DB cross-check.
