# Архитектура и принципы приложения «Управление цехом Li-Ion»

## 0. ГЛАВНЫЙ ПРИНЦИП: ПОЛНЫЙ ОФЛАЙН
**Никакого онлайна.** Приложение работает без интернета. Вся передача заданий и результатов — только через:
1. **Bluetooth** (в т.ч. mesh-сеть между устройствами)
2. **QR-коды** (камера сканирует, приложение само подхватывает задание)
3. **Текст** (отправка задания текстовым сообщением, копирование/вставка)

Следствия этого принципа:
- База данных хранится **локально на устройстве** (IndexedDB / Dexie).
- Синхронизация между телефонами/планшетами происходит **только офлайн-каналами** (BT/QR/текст), а не через сервер.
- Никаких API к внешним серверам. Supabase и любой другой облачный бэкенд **не используются**.
- Каждое устройство — самодостаточная копия системы.

## 1. Ролевая модель (цепочка подчинения)
| Роль | Кто | Может |
|---|---|---|
| `chief` | Начальник производства | Создавать список работников, логины/пароли, назначать роли; видеть все этапы; master для всех |
| `master` | Мастер цеха | Создавать/назначать задания в своём цехе; видеть все этапы своего цеха; master для worker'ов |
| `technologist` | Технолог | Править техкарты, калькуляторы, параметры процессов; комментировать |
| `worker` | Работник | Видит только свои задания своего этапа; выполняет, отмечает результат |

**Master–slave:** устройство начальника/master'а может **принудительно** дописывать информацию в приложения slave-устройств (через BT/QR пакет с флагом `forced`). Slave принимает такие пакеты всегда; master принимает от slave только данные (задания в статусе «выполнено», результаты, журналы).

## 2. Цех = набор этапов («комнат»)
Производство делится на этапы, каждый — физическая комната. Каждый этап — **независимый модуль в коде**, который можно переписать целиком, не трогая остальные.

| Код этапа | Название | Инструменты комнаты |
|---|---|---|
| `storage` | Склад материалов | Учёт входящих/исходящих партий, запасы, сроки хранения |
| `slurry` | Приготовление шлама | **Шлам-калькулятор** (пропорции PVDF/SBM/актив. материал/растворитель), база рецептов, журнал работ, комментарии |
| `coating` | Нанесение покрытия | Параметры нанесения (скорость, толщина, температура), журнал, комментарии |
| `calendaring` | Каландрирование | Расчёт обжатия, зазоры валков, журнал, комментарии |
| `sorting` | Сортировка / рубка | Размеры пластин, дефекты, журнал, комментарии |
| `assembly` | Сборка элементов | Порядок сборки (stack/z-fold), контроль полярности, журнал, комментарии |
| `electrolyte` | Розлив электролита | Дозировка, чистота, время выдержки, журнал, комментарии |
| `formation` | Формирование (ЧЦЦ) | Профили заряда-разряда, токи/напряжения, журнал, комментарии |
| `aging` | Старение | Таблица старения, отбор брака по падению напряжения, журнал, комментарии |

Общий минимум для каждой комнаты: **база данных (рецепты/параметры), журнал выполненных работ, секция комментариев**. Плюс специфический инструмент (как шлам-калькулятор).

## 3. Структура кода (модульность)
```
src/
├── core/                  # ядро: типы, БД, права, auth — меняетcя редко
│   ├── types/             # StageId, Task, User, SyncPacket...
│   ├── db/                # Dexie (IndexedDB), офлайн-хранение
│   ├── permissions.ts     # матрица прав по ролям
│   └── store/             # zustand-сторы (auth, tasks)
├── shared/                # общие UI-кирпичи (layout, карточки, QR-видео)
├── transfer/              # ЕДИНЫЙ канал передачи: Bluetooth + QR + текст
│   ├── packet.ts          # формат пакета (JSON → base64 → QR / BT-чанки)
│   ├── bluetooth.ts       # BT-обмен, mesh-ретрансляция
│   └── ingest.ts          # автоподхват входящего пакета из текста/QR
└── stages/                # ПО ОДНОМ МОДУЛЕ НА КОМНАТУ
    ├── registry.ts        # реестр этапов: метаданные + маршрут + инструменты
    ├── storage/
    ├── slurry/            # SlurryModule + SlurryCalculator
    ├── coating/
    ├── calendaring/
    ├── sorting/
    ├── assembly/
    ├── electrolyte/
    ├── formation/
    ├── aging/
    └── _common/           # JournalTable, CommentsSection, ParamDB — переиспользуются всеми комнатами
```
Правила:
- Комната импортирует только из `core`, `shared`, `transfer` и `stages/_common`. **Комнаты не импортируют друг друга.**
- Реестр `registry.ts` — точка подключения: добавил папку + строчку в реестр → комната появилась в интерфейсе.
- Любой модуль комнаты можно удалить/переписать без последствий для остальных.

## 4. Данные и синхронизация
- **SyncPacket** — единый формат переноса: `{ v, type: task|result|journal|user|forced-push, stage, payload, from, ts, signature }`.
- QR: JSON→base64→несколько QR-кадров (при больших данных). Текст: тот же base64 в сообщении. Bluetooth: те же байты по чанкам; каждое устройство ретранслирует пакет дальше (mesh).
- Конфликты: побеждает более свежий `ts`; `forced`-пакеты от master применяются безусловно.

## 5. KPI и геймификация (перспектива)
- Каждая запись в журнале комнаты — это единица учёта (что сделано, кем, когда, параметры качества).
- KPI считаются **локально из журналов**: выработка, % брака, соблюдение техкарты, скорость цикла. Дашборды: worker (свои), master (цех), chief (производство).
- Позже поверх KPI — геймификация: очки, уровни, рейтинги бригад, достижения («100 пластин без дефекта»). Всё считается офлайн из той же базы журналов.

## 6. Платформы
- **Android**: APK (Capacitor), сборка через GitHub Actions, подпись одним ключом → обновления ставятся поверх.
- **iOS / ПК**: браузерная PWA-версия (офлайн-режим Service Worker). Bluetooth в браузере ограничен → на iOS основной канал — QR/текст.
